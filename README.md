# 压缩格式迁移：gzip(旧) → xz(新)

历史分区用 gzip，新写入切换到 xz/LZMA2，而两个消费端的解码能力并不同步。
本仓库用**纯 Python 标准库**实现真实压缩、解压与数据核对：gzip(RFC 1952) 与
xz(LZMA2) 都是公开标准格式，由 `gzip` / `lzma` 标准库模块支持，**没有自创任何压缩算法**。

## 组件（各自独立运行）

| 组件 | 入口 | 职责 |
|---|---|---|
| 入仓转换器 | `python -m src.ingest` | raw 暂存 → 压缩入仓，**逐文件**登记格式与校验值 |
| 文件目录 | `data/catalog.json` | 每个文件的实际格式、文件 sha256、内容 sha256、行数 |
| 消费端 ×2 | `python -m src.consumer --name consumer-a` | 声明能力、按序读取、全程核对、断点续跑 |
| 网页控制台 | `python -m src.server --port 8000` | 声明能力 / 转换分区 / 损坏与恢复 / 核对 / 停用评估 |

## 快速开始

```bash
python -m src.seed --reset        # 生成演示数据: 5 个 gzip 历史分区 + 4 个 xz 新分区
python -m src.server --port 8000  # 打开 http://127.0.0.1:8000
python tests/e2e.py               # 全链路端到端核对 (独立临时目录)
```

## 为什么不能只改全局格式名

混合格式期间，仓库里同时存在两种格式的文件。全局"写入格式"只决定**下一个**文件
怎么写；任何一个**存量**文件是什么格式，只能查目录里它自己的登记项。目录对每
个文件登记：

- `format` —— 实际压缩格式（解码入口的唯一依据）
- `file_sha256` —— 压缩字节的校验值（发现损坏/篡改）
- `content_sha256` —— **解压后**规范字节的校验值（与格式无关，换格式重编码后必须不变，是跨格式核对的不变量）
- `rows` —— 行数（防静默漏行）

## 迁移决策：混合读取 + 按需转换，而不是全量重写

两条路的代价：

- **全量重写**：切换瞬间把所有历史分区重编码。一次性 IO/算力开销大，重写期间
  要双份存储，且重写窗口内任何失败都留下半迁移状态；好处是旧解码器可以立刻退役。
- **长期混合**：目录逐文件登记，新写作用新格式，历史分区按需（或错峰）转换。
  代价是新旧两个解码器要并存一段时间，消费端能力不对称必须被显式处理。

本实现选**混合读取 + 按需转换**，因为消费端升级节奏不受仓侧控制，全量重写并不
能免除"旧消费端读不了新格式"的窗口期；逐文件登记让两种格式可以安全共存，转换
可以按分区渐进推进、逐文件回放核对。

**旧解码器（gzip）何时能停用** —— 三个条件同时满足（`ops.retire_check`，网页实时评估）：

1. 目录中不再有任何 active 文件是 gzip（全部转换或已下线）；
2. 所有已登记消费端都声明了 xz 能力（否则转完它们读不了）；
3. 此刻全量核对通过（没有未处理的损坏）。

满足后即可从消费端删掉 gzip 解码路径；此后若发现漏网 gzip 文件，属于目录登记事故，
按损坏流程处理而不是重新启用旧解码器。

## 读到一半遇到不支持的格式怎么办

消费端** fail-fast，绝不跳过 **：

1. 按 (分区, part) 顺序读，每个文件先查目录登记格式；
2. 格式不在自己的能力表里 → **立即停下**，退出码 3，stderr 明确报出文件、登记格式、
   已声明能力和处理办法；**不跳过该文件继续读后面的**（跳过 = 静默漏行），
   不发出该文件的任何行，不伪装成"读完了"；
3. 断点只提交到**最后一个完整核对通过**的文件；升级能力（`--cap gzip,xz`）或把该
   分区转换到支持的格式后，从断点续跑，不重不漏；
4. 文件校验值不符 / 解压失败 / 内容校验值或行数不符 → 退出码 4，同样不放行任何行。
   校验在**发出任何行之前**完成，所以不存在"吐出半个坏文件"。

## 损坏与恢复、数据核对

- **损坏注入**（网页"损坏"按钮 / `ops.corrupt_file`）：翻转文件中间两个字节，目录不动。
- **发现**：审计（目录期望 vs 磁盘实际）或消费端读取时文件 sha256 不符即暴露。
- **恢复**（`ops.recover_file`）：从 raw 源按确定性切分重放出该 part，**重放内容的
  sha256 必须与目录登记一致**才允许替换，否则拒绝恢复（说明上游也变了，不能拿错数据硬修）。
- **核对**（`ops.audit`）：三层比对 —— 目录 vs 磁盘（每个文件双校验值 + 行数）、
  分区行数 vs raw 源行数、逐 part 内容 vs raw 源重放内容。任何一层不符 `ok=false`。

## 网页 API

| 端点 | 说明 |
|---|---|
| `GET /api/state` | 目录快照（含逐文件实时状态）+ 停用评估 |
| `POST /api/seed` `{reset}` | 生成演示数据 |
| `POST /api/ingest` `{partition, parts}` | 入仓指定分区（按当前写入格式） |
| `POST /api/write_format` `{format}` | 切换**新写入**格式（不改存量） |
| `POST /api/convert` `{partition, target}` | 转换指定分区，回放核对后原子替换 |
| `POST /api/corrupt` `{file}` | 损坏一个文件（故障注入） |
| `POST /api/recover` `{file}` | 从 raw 源核对恢复 |
| `POST /api/capabilities` `{name, capabilities}` | 声明消费端解码能力 |
| `POST /api/run_consumer` `{name, from_scratch}` | 以独立子进程运行消费端 |
| `POST /api/audit` | 全量核对 |

## 数据布局

```
data/
  raw/<分区>.jsonl                        # 上游源（模拟对象存储暂存）
  warehouse/dt=<分区>/part-NNN.jsonl.gz|xz # 仓内压缩文件
  catalog.json                            # 文件目录（期望值）
  out/<消费端>.manifest.json               # 读完清单（行数 + 读取链哈希）
```
